### Fixed

- **Halo 2 generated profiles rejected as "damaged"** (confirmed bug + fix, 2026-06-25 xemu runtime pass — the in-game acceptance test the signature work had deferred). The hub's generated/edited H2 player profiles were rejected in-game ("We're having problems with this profile because it's damaged. Would you like to delete it?"). **Two root causes**, both in `internal/halosave` (identical on `main` and `feat/gamertag-system`): (1) **The 20-byte save signature was never recomputed.** `digest.go`'s `RecomputeDigest` was an unimplemented stub returning `ErrDigestUnresolved`, so every builder fell back to *preserving the template's* digest. A name/appearance edit changed the content but not the digest → the HMAC no longer matched → "damaged". The algorithm was in fact already cracked offline (the Original-Xbox **roamable** save signature: `sig = HMAC-SHA1(AuthKey, buf[:sigOff])`, `AuthKey = HMAC-SHA1(XboxGlobalKey, title_cert_sig_key)[:16]`) but only landed in the Python reference, never the Go port. `RecomputeDigest` now implements it for CE and H2; `Build*` always re-signs (`recomputedDigest`, `DigestResolved()==true`). The key derivation uses **only** a global Xbox constant + the title's XBE cert key (NO console/HDKey/EEPROM input), so it is **per-title roamable** — the hub signs centrally; the nxdk client needs no local-console signing. Verified: recompute reproduces the stored digest byte-exact on every real sample (CE 23/23, H2 3/3) and the embedded CE/H2 cert keys match the retail `default.xbe` certs. (2) **The name write clobbered a per-profile sub-block.** The H2 "name buffer" was modelled as 0x110 bytes (0x08..0x118); writing a name zero-filled all of it, wiping the fixed 16-byte `0xFF` field at 0xEC..0xFB and the bytes at 0xFC/0x101/0x102 (real data in all 4 samples). The name field actually ends at **0xEC** (`h2pNameBuf 0x110 → 0xE4`), preserving that sub-block. **xemu runtime confirmation:** the previously-damaged `CARTOG` (stale digest) reproduces the exact dialog; the re-signed/length-fixed profile and a byte-identical clone of a real profile both load cleanly into the H2 main menu (disk-overlay test, stock `hdd*.qcow2`/`eeprom.bin` untouched). Regression tests added (`TestRecomputeReproducesRealDigests`, `TestBuildH2ProfileIsCorrectlySigned`, `TestH2ProfileNameWritePreservesSubBlock`, `TestBuildUnchangedH2CloneByteIdentical`). **Gates the gamertag system** — `feat/gamertag-system` inherits the fix via `internal/halosave`; land the same commit on `main`. (Python reference `docs/lan-hub/reference/halo_save_formats.py` updated to match: `name_buf 0x110 → 0xE4`; its `recompute_digest` was already correct.)

### Added

- **Gamertag identity system (`feat/gamertag-system`)** — a unified "one gamertag = your in-game name" layer over the LAN-hub `halosave` generator. The gamertag is a field on the **user** record (`users.gamertag`, **separate from the account `username`** which carries no Halo constraints) and is length-capped to `GamertagMaxLen` (**11** printable-ASCII chars — CE's `blam.sav` name buffer is 24 bytes ⇒ ≤11, the tighter of the two; H2 allows ~113). It drives **two player profiles** (CE + H2), edited side by side at `/gamertag/` (RequireAuth) but stored as **separate** records; the profiles don't store the gamertag — the generate hooks resolve it from the user via the `user` relation, and `users_gamertag_regen` re-generates the profiles whenever it changes. **Generate-on-save:** whenever the gamertag, a profile, or a gametype changes, a PocketBase record hook regenerates the actual signed Xbox save file(s) and stores them on the record — the deployable tar of the FATX save dir on a `save_bundle` file field + sha1/size/digest metadata on `save_info` (`internal/saveartifact` → `internal/halosave`; `hooks/{save_artifact,h2_profiles_generate,ce_profiles_generate,gametypes_generate,users_gamertag_regen}.go`). Both player profiles are **full + signed**: the **CE profile** is `blam.sav` (512 B — name @0x00 + armor color @0x18 + thumbstick/button presets @0x28/0x29, signed at 0x30 with the same per-title HMAC as the CE gametype; format cracked, see `docs/gamertag-system/CE-PROFILE-FORMAT.md` + the new `halosave.CEProfileBuild`, signing verified byte-exact vs a real captured profile) and the **H2 profile** is the 500-byte `profile` (appearance/controls). A gamertag generates **only** these two player profiles — it does NOT set the Xbox console name (`NICKNAME.XBN`), which is a per-console setting unrelated to a user's identity (the M26 fleet auto-naming of xemu instances via `internal/podman` is separate and unchanged). Four new collections registered through `identity.go` phase 5 — `ce_profiles`, `h2_profiles` (owner-scoped), `gametypes` + `game_titles` (the XBE upload library — **not** the M13 `games` collection; read by any authed user, mutated by the new **`organizer`** baseline role or admins via the `organizerOrAdmin` rule). New **organizer** route group (`/organizer/gametypes/` library editors, `/organizer/games/` name+description+file uploads) gated by `requireOrganizer` (`auth.hasRole('organizer')` works for free — `/api/me` already returns roles). The LAN download API gains per-gamertag endpoints: `GET /api/lan/saves/identity/{gamertag}` (resolves the user by gamertag → a manifest of their CE+H2 profiles plus all gametypes + games, each with a download URL) and `GET /api/lan/saves/file/{kind}/{id}` (streams the stored bundle/upload with Range support). Generated files are **correctly signed** — the halosave 20-byte digest is now implemented (`RecomputeDigest` for CE + H2; all builders always re-sign; per-title/roamable so the hub signs centrally) and verified in-game (Halo 2 accepts the profiles), fixing the "damaged profile" rejection the old template-patch/stale digest caused. nxdk client wiring deferred (the two per-gamertag endpoints are the contract). Verified: `go build`/`vet`/`test` (halosave CE `blam.sav` signing is byte-exact vs a real captured profile; saveartifact unit; a PocketBase integration test proving CE + H2 generate signed bundles, the gamertag-rename cascade regenerates, and a gamertag-less user is rejected), `pnpm check`/`lint`/`test`/`build`, plus a live isolated-port server run (the 11-char + printable-ASCII cap is enforced; creating the CE profile generates a **signed `blam.sav`** — correct name/color/presets, HMAC over `[0:0x30]` matches the stored digest — and the H2 profile a signed bundle; the manifest resolves a gamertag to both profiles; editors render with zero console errors). See [docs/gamertag-system/README.md](docs/gamertag-system/README.md).
- **BSP-editor — material-name semantic priors + offline pre-baking (`feat/bsp-editor`).** The extractor (`scripts/game-geometry/extract_bsp.py`, schema 3) now emits each surface's **shader name + a coarse semantic class** it already computes en route to material colour (`materials` / `material_semantic` / `triangle_material`), and the editor's auto-tagger consumes them as **priors** over the pure-geometry/enclosure guess (`semanticToTag` + the combine in `autoClassify`): floor/ramp/grate materials → walkable (orientation-guarded so no vertical "floors"), ceiling/light/sky → dropped overhead, wall/glass only confirm geometry — so genuine ramps/floors are never eaten and unknown names fall through to geometry (**no regression**). Geometry can't tell a floor from the ceiling above it or terrain from sky; the name can — on Blood Gulch this reclassified **~1,400** outdoor-terrain triangles from mis-culled `ceiling` back to `floor`. A **degenerate stray-line cull** (`degenerateTriangleIndices`, area `< 1e-5` wu²) drops the BSP's zero-area/collinear artifacts the lower-tunnel "stray lines" came from (Chill Out 81, Prisoner 11, Blood Gulch 0), seeded on editor load so editor-save matches the offline bake. New `scripts/game-geometry/bake_spectator.ts` pre-bakes spectator meshes **headless** by reusing the editor's pure core (Node type-stripping; the manual `*.tags.json` sidecar stays authoritative) and patches the manifest so both visualizers serve the culled mesh. Pre-baked Chill Out / Prisoner / Blood Gulch. Unit-tested (`semanticToTag`, the prior combine, the degenerate cull, the schema-3 parse + fail-safe degrade in `normalizeMesh`). Game-derived cache stays git-ignored; the committed product is the extractor + baker + frontend.

### Changed

- M26 — Container HDD provisioning switched from a **full per-instance copy** to a **qcow2 copy-on-write overlay**. One read-only root (`containers/xemu/shared/hdds/_default.qcow2`, configurable via `CONTAINERS_ROOT_HDD`) is shared by every instance; `internal/podman` `Manager.Create` → `provisionOverlay` ([overlay.go](internal/podman/overlay.go)) runs `qemu-img create -f qcow2 -b _default.qcow2 -F qcow2 <name>.qcow2` so each instance writes only its deltas (create is near-instant; N instances no longer cost N×~8 GiB). xemu (a qemu fork, stock qcow2 block driver) reads the canonical disk from the root through the backing chain — verified by a real `xemu` overlay boot (QMP `running`, ~642 KiB deltas to the overlay, root byte-untouched) plus concurrent-overlay + `qemu-io` mechanics checks. The **root is frozen read-only (0444)** by `freezeRoot` on first overlay create (modifying a backing file corrupts every overlay above it; `CleanupOrphans` already skips `_`-prefixed baselines), and the **backing path is stored relative** so it resolves both on the host (`./containers/xemu/shared/hdds`) and inside the container (`/shared/hdds`) and survives the dir moving. `Manager.Remove` deletes the overlay; `03-setup-hdd.sh` no longer copies — it just injects the overlay's `hdd_path` (with an in-container `qemu-img` fallback, never a full copy). New host prerequisite: `qemu-img` (`CONTAINERS_QEMU_IMG_CMD`). eeprom/flashrom are image-level and unchanged. **⚠️ Updating the root requires deleting every overlay and re-creating the instances.** Unit-tested (`overlay_test.go`). See [M26](docs/milestones/M26-hdd-overlay-provisioning.md).
- M26 — Container teardown is now **symmetric** with create: deleting a container (`Manager.Remove`) removes _every_ per-instance (non-shared) file it generated — the HDD overlay, the xemu config dir (which holds the per-instance eeprom + toml/ssl/shaders/X state) and the browser profile — via a new shared `removeContainerFiles` (also used by `DeleteFiles`). ### Fixed

- `apiBaseURL()` now honors the page's `https:` protocol in dev (was hardcoded `http`).
- Envelope `seq` no longer hardcoded to `0`. New per-(instance, class) counter on the runner (`seqByClass` + `seqMu`) bumps each `marshalClassEnvelope` call, so clients can detect drops / out-of-order delivery / retransmits (M06).
- `xbox.name` now resolves for every observed container shape (dashboard-idle and in-game alike). `xbox.ReadConsoleName` swaps its old 8-byte `00 00 00 00 30 53 11 9E` anchor for a 12-byte `NICK` header anchor (`4B 43 49 4E 01 00 00 00 00 00 00 00`) and dispatches on the 4-byte record tag at NICK+12 — type A (`04 00 53 4D`, observed on Halo containers) or type B (`30 53 11 9E`, canonical `NICKNAME.XBN`, observed on UnleashX-booted containers). Triangulated against four live containers (Whicker / Cupid / Crazy / charr) (M06).
- Scenario class envelope now re-broadcasts when its observable fields fill in lazily after the Ready→Live snapshot already shipped. New `(r *runner).maybeEmitScenario` watches a packed fingerprint of `len(PlayerSpawns)` / `len(ObjectTypes)` / `len(PowerItemSpawns)` plus `Fog` / `TagCache` presence on `cache.GameData` and re-emits when the fingerprint changes; `broadcastSnapshot` syncs the fingerprint to its own emission so phase transitions don't double-emit. Fixes the UI's empty `player_spawns` / `object_types` / `power_item_spawns` / `tag_defs` tabs during active matches even though the backend cache was populated (M06).
- `scenario.map` now resolves on the Xbox build. Replaced the halocaster.py-era `AddrMultiplayerMapName = 0x2E37CD` low-GVA read (which returns `""` on Xbox) with a `Reader.readScenarioTagName()` helper that walks the tag instance array for the entry whose `data_ptr` matches the global scenario pointer and reads its name (e.g. `levels\test\downrush\downrush`). Used in both `composeGameData` and the `scenarioStaticCache` populator. `AddrMultiplayerMapName` deleted; no remaining callers (M06).
- Scenario envelope `player_spawns[].gametypes` now serializes as a JSON number array (e.g. `[13,0,1,0]`). Previously came across as a base64 string (`"DQABAA=="`) because the field was declared `[]uint8`, which Go's `encoding/json` aliases to `[]byte` and marshals as base64. Switched to `[4]uint8` (fixed-size arrays of bytes don't trigger the special case). Frontend types already expected `number[]`, so no parse-side change (M19).
- Scenario envelope `object_types` / `power_item_spawns` no longer permanently empty after a transient cold read on scenario load. `ensureScenarioStatic` flipped `Filled = true` unconditionally after the first attempt, so if `readObjectTypes` (depends on object-type cache range Lo/Hi being engine-populated) or `readPowerSpawnScenarios` (depends on `tagInstBase` being warm) returned empty on that first call, the empty result was locked in for the lifetime of the scenario. Now each field is re-read while still empty, and `Filled` only flips once all critical readers have actually produced data (M19).
- Scenario envelope `object_types` now populates with all 11 Halo CE Xbox object type entries (biped, vehicle, weapon, equipment, garbage, projectile, scenery, machine, control, light_fixture, placeholder) and engine-reported datum sizes. Previously empty: `RefAddrObjectTypeDefRangeLo/Hi` were dereferenced as pointers when they're actually literal address bounds, and the per-type struct pointers in the array are low-GVA (engine .data section) requiring per-pointer translation via `RefreshLowHVA`. Per-type name field at +0x00 turned out to be a self-pointer/vtable on Xbox (halocaster.py's "string pointer at +0x00" was wrong), so names are hardcoded from Halo CE's fixed 11-type order (M19).
- Scenario envelope `power_item_spawns` now populates with every respawnable scenario item placement (powerups, heavy weapons, grenades — whatever the level designer assigned a respawn time). Previously empty due to a tag-handle vs s32-index read bug at scenario_item+0x5C plus a wrong itmc-tag-data offset chain. `OffScenItemTagIndex` is now read as a u32 handle (high16=salt, low16=index, 0xFFFFFFFF=empty); the itmc default spawn time is read directly at tag_data+0x0C (no PC-style indirection through +0x14); the per-placement spawn-time override at scenario_item+0x0E takes precedence when non-zero. Values multiplied by `TicksPerSecond=30` so the wire stays in tick units (M19).
