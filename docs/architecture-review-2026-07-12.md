## How to read this

This is a retrospective on the *major* structural decisions in xemu-cartographer and its interfaces to `halo-offset-mapper` and the offset-hunting rig. It is deliberately not a nitpick list. Each decision is covered in four parts:

1. **What** — the current structure/approach.
2. **Why** — the original rationale, quoted from the ADR/doc/comment/commit where it exists, or marked *undocumented → inferred from code* where it does not.
3. **Assessment** — has it aged well or is it brittle.
4. **Better?** — a concrete recommendation (keep / refactor / replace) with rough effort (S/M/L) and risk (low/med/high).

Claims are tagged **[doc]** when the repo states the rationale in words (quoted) and **[inf]** when I am inferring from the code or history. A ranked "worth revisiting" table (impact × effort) closes the document, followed by a reference appendix.

A note up front, because it recurs: **the decision record is split across branches.** `main`'s `docs/decisions/` holds only ADR-0001 (version-from-git-tag) and ADR-0002 (unified audit_log). The two ADRs most relevant to recent work — **ADR-0003 (programmatic xemu input: sendkey vs. uinput pad)** and **ADR-0004 (ISO-boot provisioning)** — are *Accepted* but live only on `feat/xemu-input-sendkey` / `feat/iso-boot-provisioning`, invisible from `main`. This matters for several sections below and is itself finding #3.

## System at a glance

A single Go binary (`cmd/server`) runs four concurrent systems plus an optional fifth (`CLAUDE.md:89-95`): PocketBase (REST + JWT auth + SQLite + static file server on `:8090`), a Disgo Discord bot, a `coder/websocket` hub, the scraper manager (one goroutine per xemu instance, reading guest memory and broadcasting per-instance rooms), and — gated by `CONTAINERS_ENABLED` — a podman provisioner plus a discovery watcher that auto-attaches scrapers as xemu instances appear. The SvelteKit SPA is built static into `pb_public/` and served same-origin by PocketBase; per-container kiosk/VNC ports stay bound to `127.0.0.1` and are reached only through a same-origin reverse proxy so a single public port suffices behind cloudflared.

The through-line of the architecture is **"one immutable shared base, cheap disposable per-instance layers"**: one canonical Halo-installed `_default.qcow2` with per-instance copy-on-write overlays; one shared origin/port with per-instance rooms and tokens; one scraper codebase with per-game offset packages. That philosophy pays off almost everywhere. The two places it strains are (a) where a *persisted record* is trusted as ground truth over *live runtime* (tonight's proxy bug) and (b) where *schema* has to evolve on an *existing* database.

## Executive summary — top findings

1. **The kiosk reverse-proxy trusts `state.json` over live podman, and that is exactly tonight's 502.** `Manager.Get` returns a persisted `ContainerInfo` with no liveness check; the proxy then dials the browser port through `dialWithRetry`, whose hard 10 s deadline turns a *recorded-but-dead* container into a 10-second hang surfaced as a 502. The retry is correct for a *booting* container but cannot tell "booting" from "never coming up." Small, contained fix; high operational impact. **(Finding #1 — revisit first.)**

2. **Version-migration brittleness is real and structural, and it's the schema path, not the toolchain.** PocketBase's own migration framework is not used at all — all 26 collections are defined in Go and re-applied inside `OnServe`, using a *create-fresh-or-touch-rules-only* pattern. Add a field and boot against an existing `pb_data` and the field silently does not appear; every real schema change needs a bespoke hand-written idempotent shim. The ephemeral dev DB hides this until a production upgrade. A PocketBase version bump would compound it (raw `core.*` field API used across ~29 files, never yet bumped off the v0.36.7 template pin). **(Finding #2.)**

3. **The decision record is fragmented and mis-numbered.** ADR-0003 and ADR-0004 are Accepted but stranded on feature branches; meanwhile `main`'s `M08-roles-permissions.md:41` says *"ADR-0003 is not needed"* referring to an entirely different (never-written) roles decision — a numbering collision that will confuse anyone reading `main`. **(Finding #3.)**

4. **Auth has two quiet fail-open footguns.** If `OVERLAY_TOKEN_SECRET` is unset the server generates an ephemeral secret and only logs a warning — silently invalidating every minted overlay token on each restart in prod; and if `WS_ALLOWED_ORIGINS` is unset the WebSocket endpoint accepts all origins. Both are dev-friendly defaults that fail open in production. Also: "station-token" **does not exist** anywhere in the repo — the real schemes are the overlay-token and the kiosk `?token=` PocketBase-user JWT. **(Finding #4.)**

5. **Live game vitals are ephemeral by design, and the replay hooks that were built are dormant.** Health / shields / overshield / camo / the team-score *timeline* stream on the `tick`/`game` firehose and are never persisted; the durable unit of record is the end-of-match box score. This is a deliberate "current-state broadcast, not event-sourced" choice — but the two capabilities that would make matches replayable (`games.snapshot_blob`, a `tick → pb:game_events` capture policy) exist and are wired to nothing. **(Finding #5.)**

6. **The input/host-runner subsystem is well-designed but unverified-live and off `main`.** ADR-0003's empirically-grounded conclusion (QMP `sendkey` can't drive the Xbox controller; the uinput virtual pad and the shared-with-admin RFB keyboard channel can) is sound, and the arbitration model (byte-identical to the admin's channel, with an explicit `Arbiter`) is elegant. But full live container-drive verification was repeatedly sandbox-blocked, and all of it sits on `feat/xemu-input-sendkey` (27 commits ahead of `main`, never merged). **(Finding #6.)**

The remaining sections cover the read path, provisioning, the SPA/same-origin model, and the read-only induction methodology — all of which have largely aged well and are recommended **keep**, with targeted hardening.

## 1. Container reverse-proxy trusts `state.json` over live podman (tonight's 502-hang)

**What.** A container pair is described by a `ContainerInfo` — just `Name`, `Index`, `Ports`, `Created` (`internal/podman/state.go:6-11`); there is no status/PID/health field. The `Manager` loads these once at construction from a `Store` (`NewManager` → `store.LoadAll()`, `podman.go:83-92`), whose production implementation is the PocketBase `containers` collection (`internal/pocketbase/resolvers/containers.go`). This collection is the direct descendant of a literal `containers/state.json` file — commit `fc52399` replaced "containers/state.json with a `containers` collection," and the dev seed still "mirrors the legacy state.json shape" (`internal/pocketbase/seed/containers.go:17-19`).

`Manager.Get` (`podman.go:659-667`) locks the map, looks up the name, and returns a copy. It never shells podman. The kiosk proxy (`internal/pocketbase/routes/containers/proxy.go:63-129`) does `info, ok := Manager.Get(name)` → 404 on miss, then builds the upstream from `info.Ports.BrowserWeb` and dials it through `dialWithRetry` (`proxy.go:131-152`), which loops `net.Dialer.DialContext` against a hard `deadline := time.Now().Add(10 * time.Second)`, sleeping 250 ms between attempts.

The failure mode: a container that is *recorded* but *not running* passes the `Get` check (existence ≠ liveness), so the request enters `dialWithRetry`, every attempt gets `ECONNREFUSED` on `127.0.0.1:<BrowserWeb>`, and the loop runs the full ~10 s before returning the dial error — which `httputil.ReverseProxy` surfaces as **HTTP 502**, which cloudflared passes through. Confirmed by reading the code directly; the "tonight" incident is the textbook instance of it. Notably `Manager.List` is even commented *"enriched with live podman status"* (`podman.go:588`) but its body returns cached info only — the comment is stale.

**Why.** Two rationales, both documented, both individually sound:

- *Why persist container state at all.* Port assignments are index-based and must survive a server restart — `nextIndex` reuses the lowest free index and ports derive from it (`state.go:15-25`, `podman.go:103-104`); the dev snapshot is described as *"Idempotent across reboots"* (`seed/containers.go:33`). A restart must not forget which pairs exist or reshuffle their ports. **[inf, from the index/port design; not stated as one sentence.]**
- *Why `dialWithRetry`.* Quoted verbatim, `proxy.go:107-109`: *"The browser container's HTTP listener (s6-overlay → nginx) takes several seconds to come up after `podman start`. Without a retry, the user's first iframe load races that boot and gets a 502."* And `proxy.go:131-134`: *"retries a TCP dial for up to ~10s … Once the listener is up, the first attempt succeeds with no measurable overhead."* This was added in commit `173ed0f`. **[doc]**

Neither rationale anticipated the *third* state — recorded-but-dead — and `M03-container-lifecycle.md:8` shows why: the podman package was ported *"as-is (clean, no known bugs)"*, i.e. carried over on the assumption it was correct; the state-vs-reality drift was never on the milestone's radar. **[doc]**

**Assessment.** The persisted store is right and should stay. The bug is a *missing reconciliation between record and runtime*, and it manifests only on the one hot path (the kiosk proxy) that never calls the live-status primitives that already exist elsewhere. The drift vectors are numerous and ordinary: server restart with pairs stopped, `podman system prune`/`rm` out-of-band, a crashed browser container, a host reboot. The mitigation primitives are *already in the codebase but unused on this path* — `Status` (`podman.go:602-626`, `podman inspect --format {{.State.Status}}`) returns live status, and the kiosk handler simply doesn't consult it. The 10 s deadline is the amplifier: it exists to smooth a legitimate boot race but cannot distinguish "listener coming up in 3 s" from "listener will never come up," because the only liveness signal it consults is the dial itself.

**Better? — Refactor (small, low risk).** Gate the proxy on liveness before entering the retry, and make the dial bounded and configurable:

- Before proxying, check that the container serving `BrowserWeb` (the `<name>-browser` half) is actually running — reuse the existing `podman inspect` path (a `Manager.IsRunning`/`KioskLive` helper) with a short internal timeout — and return a fast **409** (or 503) `"container not running"` instead of dialing a dead port. An authoritative `inspect` distinguishes *not-running* (fast fail) from *running-but-booting* (keep the retry), so it preserves the boot-race behavior that `dialWithRetry` was built for. This also makes the failure legible in DevTools (a clean 409) instead of a 10 s 502.
- Make the per-dial timeout short and the total retry budget configurable via env (defaults preserving today's ~10 s boot-race window), so even a filtered-port edge case can't hang.
- Optionally, add a one-time `record → podman ps` reconcile at `NewManager` so a stale record is caught at boot rather than at first request. Larger blast radius; treat as a follow-up, not part of the minimal fix.

Effort **S**, risk **low** — the change is additive, touches one handler plus one Manager method, and is straightforwardly unit-testable (dial-timeout behavior against a live listener vs a dead port; running-state parsing). This is the single highest impact-per-effort item in the review.

## 2. Copy-on-write overlays + ISO-boot provisioning

**What.** Every instance shares one canonical, read-only, Halo-installed `_default.qcow2` and gets a thin per-instance qcow2 overlay that records only its deltas. `provisionOverlay` (`internal/podman/overlay.go:63-96`) runs *before* container creation (so a missing/locked root aborts cleanly), errors loudly if the root is absent, `chmod 0444`s the root, is idempotent (reuses an existing overlay after a crash-and-recreate), and runs `qemu-img create -f qcow2 -b <rootName> -F qcow2 <name>.qcow2` with `cmd.Dir = hdds` so the backing reference is a bare relative basename. The in-container init script `03-setup-hdd.sh` normally just injects the pre-created overlay path and *explicitly refuses to ever full-copy the multi-GiB root*.

ISO-boot provisioning (ADR-0004, on `feat/iso-boot-provisioning`) is the companion: attach a per-instance game XISO as the DVD (`CreateOptions.GameISO`, bind-mounted read-only at `/game.iso`), and patch `dvd_path = '/game.iso'` into the instance TOML so the Xbox boots the disc directly. The overlay stays lean (no game on the HDD); the game is chosen per instance.

**Why.** This is the best-documented decision cluster in the repo, with live proof. On overlays, `M26-hdd-overlay-provisioning.md:9-15` (echoed in `overlay.go:41-49`): *"Previously every container got its own ~8.4 GiB `cp` of the root disk (slow to create, N×8 GiB of disk for N instances). Now one canonical read-only root qcow2 is shared by all instances, and each instance gets a thin overlay that records only its own deltas."* The relative-backing choice is justified because the `hdds` dir is bind-mounted at a different path in-container vs on-host, so an absolute path *"would break inside the container"* (`overlay.go:51-57`), and it's enforced by a unit test asserting the backing filename. Freezing the root to `0444` is justified because *"Modifying a backing file corrupts every overlay above it"* (`M26:53-57`). M26 records real verification: qcow2 backing-chain mechanics via `qemu-io`, a real xemu boot against an overlay (overlay grew ~642 KiB, root sha256 unchanged), and six concurrent overlays over one root all isolated. **[doc]**

ADR-0004 is equally empirical. Its A/B table (reading the running XBE certificate title over QMP `memsave` on the *unmodified* root) shows no disc → `UnleashX`, `Halo CE.iso` → `Halo`, `Halo 2.iso` → `Halo 2`, and concludes: *"`Halo 2.iso` booting Halo 2 — with only Halo CE installed on the HDD — proves the disc is the boot source, not the HDD install."* The decision explicitly ships "attach ISO as DVD" and does **not** bake auto-launch into the root, keeping the master image unmodified. **[doc]**

**Assessment.** Aged well, and verified to a standard most of the repo doesn't reach. The design is coherent (both decisions serve "lean disposable per-instance layer over an immutable base") and the failure modes are documented rather than latent. The genuine fragilities are inherent to qcow2 backing chains and are already flagged in three places: editing the shared root invalidates every overlay (there is *no* in-place root edit that preserves overlays), and `freezeRoot` is best-effort — on a host where the `chmod` can't take, the "fail loudly on accidental edit" guard silently doesn't exist and only qemu's own read-only open protects the chain (`overlay.go:99-117`). Pre-existing full-copy disks (`nexy.qcow2`, etc.) are not auto-migrated and silently sit outside the CoW model. ISO-boot's one thin spot is observability: because this xemu build strips `screendump`, "did it actually boot the game?" is confirmable only through memory reads, not a framebuffer grab (ADR-0004 caveat).

**Better? — Keep, with minor hardening (S, low).** No structural change. Consider: (a) make the root-freeze failure a hard error (or a loud startup healthcheck) rather than best-effort, since a silently-unfrozen root is the one catastrophic path; (b) a `doctor`/preflight check that verifies `_default.qcow2` presence + read-only-ness and warns on legacy standalone disks; (c) fold ADR-0004 into `main`'s decision log (see finding #3) so the ISO-boot rationale is discoverable without checking out a branch. The auto-launch lever ADR-0004 deliberately built-but-didn't-wire is fine to leave dormant — it is documented as a conscious "kept for a future image" trade-off.

## 3. Scraper read path — `/proc/<pid>/mem` vs QMP `memsave`

**What.** The live read path is a **two-channel hybrid**, and this is the single most important fact about it: QMP is used *only* for address translation (guest-virtual → guest-physical → host-virtual), a handful of times at attach and on XBE swaps; *all* actual game-state reads go through `/proc/<pid>/mem` via `syscall.Pread`. The bridge is `internal/xemu/{mem.go,qmp.go,instance.go}`. `Mem` holds an open fd to `/proc/<pid>/mem` plus a `base` (host VA of guest physical 0); `readAt` (`mem.go:28`) is the sole read primitive; high guest VAs (≥ `0x80000000`) are reached by flat arithmetic off `base` with no per-read QMP round-trip, and low GVAs are pre-translated once at `Init` and re-translated on demand via `RefreshLowHVA` when an XBE swap moves the physical pages. The QMP client uses HMP `human-monitor-command` (`gpa2hva`/`gva2gpa`), *not* the `memsave` verb. The PID is discovered by globbing `/proc/*/cmdline` for the QMP socket path (`instance.go:117-147`). Per-game offsets live only in each game's package (`internal/scraper/haloce/offsets.go` for CE; the H2 package exists only on an unmerged WIP commit, not on `main`).

**Why.** The split is documented, and the two projects deliberately chose *different* channels. `docs/XEMU-TEST-SETUP.md:34-44`: *"This xemu build strips `screendump`/`pmemsave` — use QMP `memsave` for targeted reads … Cartographer reads `/proc/<xemu-pid>/mem` … The offset-mapper scripts avoid this entirely by reading over QMP `memsave` instead."* The performance rationale is explicit at `haloce/offsets.go:79-82`: *"Go reads /proc/<pid>/mem directly; QMP-cache hack from HC unnecessary."* At the Live poll cadence (~10 ms, up to ~3 reads per engine tick), a QMP text round-trip *per field* would be prohibitive; `Pread` on an open fd with pre-translated addresses is a direct syscall. The container-deployment rationale is the load-bearing one, `M01-xemu-memory-bridge.md:13`: xemu's netplay caps make the process non-dumpable and flip `/proc/<pid>/*` to `root:root`, so *"M3's containerised deployment runs the server rooted inside the container PID namespace and side-steps both."* And the read-only posture is deliberate — `M24-remote-game-setup.md:6`: *"Today every memory access in this project is read-only (`internal/xemu/mem.go` is `Pread`-only over `/proc/<pid>/mem`)."* There is **no ADR** for any of this; the rationale lives in milestone docs, the test-setup doc, and code comments. **[doc, with the ADR-absence itself documented]**

**Assessment.** The channel split is the right call and has aged well: reads are hot and must be a syscall, translation is rare and is exactly what a monitor is for, and leaning on QMP `gpa2hva`/`gva2gpa` makes the whole thing ASLR-robust by construction. The residual fragilities are real but mostly inherent to live-memory scraping and are largely acknowledged in-code:

- *Offset drift across game/emulator builds* is the dominant, repeatedly-bitten failure — offsets were ported from a Halo-PC tool and every constant must be re-verified against the Xbox build (M19 is a whole milestone about turning silent bad offsets into loud errors). Offsets are pinned to `xemu 0.8.136`; a newer xemu that shifts guest layout would break the active read path exactly as the PC→Xbox mismatch did. (This overlaps finding #2 / candidate D.)
- *Torn reads*: the read path never pauses the vCPU, so a multi-field player/object walk is a sequence of independent `Pread`s with no snapshot semantics and can catch a tick mid-update. The codebase is aware — `M24:35` prescribes QMP `stop`/`cont` around *writes* — but accepts the hazard un-mitigated on the read path.
- *PID re-discovery* happens once per `Init`; a restarted xemu needs the discovery watcher to notice the socket drop and re-attach, and there's a multi-poll window where a dead xemu is still "known."
- *`base` staleness*: high-GVA reads all derive from a single `base` captured once at `Init`, with no refresh path equivalent to `RefreshLowHVA` if the host RAM mapping ever moved (e.g. across a savestate load). **[inf]**

**Better? — Keep (M to change, high risk to replace).** The hybrid is correct; do not replace it with pure `memsave` (too slow for the hot path) or pure arithmetic (loses XBE-swap correctness). Worthwhile, lower-risk hardening: add a `base`-revalidation/refresh path symmetric to `RefreshLowHVA`; consider coalescing adjacent field reads of large object arrays into a single `Pread` to cut syscall overhead at fleet scale; and treat the `xemu 0.8.136` pin as a first-class compatibility contract (a documented "supported emulator build" with a startup magic-value probe that fails loudly on an unexpected build, extending M19's approach). The read-only boundary should stay firmly where it is.

## 4. extract → emit → persist, and the ephemeral dynamic state

**What.** The pipeline is: **extract** (read `/proc` at offsets into Go structs — `haloce/reader.go`, e.g. health/shields/overshield/camo at `reader.go:897-909`), **emit** (fan per-class WebSocket envelopes to per-instance rooms — `manager/runner.go`), **persist** (write PocketBase rows). There are two persist paths: a structured end-of-game write at the Live→Ready edge (`games`/`game_players` via `internal/games/persist.go`), and an optional event-firehose sink that only fires if an operator configures a `capture_policies` row routing a class to `pb:game_events`. The phase model (M05) restructured the scraper around an Idle/Ready/Live state machine with an authoritative structured `instanceCache` as the source of truth, and a `PreviousGame` slot captured on the Live→Ready transition (with a `defer` so a mid-match crash still captures the just-ended match).

The consequential fact: **player health, shields, overshield, active-camo, and the team-score *timeline* are live-only.** They flow memory → `TickPlayer`/`TeamScore` → the `tick`/`game` WS classes → subscriber, and are never durably written — there is no collection field for them, a grep for writes is empty, and the end-of-game projection (`games_persist.go:102-111`) maps only kills/deaths/assists/score/team. What *is* persisted is the finished-match box score (`games`, `game_players`, `ratings`, and optionally back-stamped `game_events`). Two nuances: discrete powerup/team-score *events* *can* be captured if an operator opts into a sink (the event taxonomy has `PowerupPickedUp`/`TeamScore`), but the continuous per-tick *values* cannot; and `games.snapshot_blob` (a JSON column explicitly *"for replay/debug"*) is defined but **never written** — always null.

**Why.** Documented as a deliberate "current-state broadcast + end-of-match box score," not an event-sourced replay system. The clearest statements are in `docs/websocket-api.md`: the firehose classes (`tick`/`objects`/`debug`) are labeled *"Firehose … not stats"* and *"exist for live overlays … not stats. Only join their rooms if you're building a visualizer, because subscribing makes the server do the per-frame reads"* (`:554-558`); the `game`/`event`/`previous_game` triplet is *"exactly three classes"* a stats app wants (`:26-29`); `previous_game` is *"the cleanest hook for 'a game just finished, record it'"* (`:297-299`). PB persistence was explicitly out of scope for the phase-model refactor and deferred to M13, *"leav[ing] the in-memory `previous_game` shape such that a future flush is straightforward"* (`M05:33`). The recovery model is documented as latest-state + event-log replay, not tick history (`CLAUDE.md:213`), and reads are demand-gated — with no subscriber and no capture policy, the firehose isn't even produced (`manager/demand.go`, `capture.go:52-53`: *"an empty Sink means broadcast-only (no persistence)"*). On `feat/match-stats`, the "why `games`, not a separate `matches`" note is explicit: hardening the existing already-read backbone beats a duplicate source of truth. **[doc]** What is *not* documented anywhere in words is the vitals-specific rationale — no sentence says "we don't store per-tick health because of volume." That is inferable from the firehose framing + the ~30 Hz cost + the demand-gated design, and the one design doc that most likely states it (`atlas/new_json/04-ground-up-rebuild.md §5`) is gitignored and unreadable. **[inf]**

**Assessment.** As a design choice this is defensible and internally consistent — the durable unit is "a finished match's box score," and vitals are treated as disposable render-time telemetry, which is a reasonable product stance for a tournament/stream tool. It has aged fine *for stats*. The brittleness is a *capability ceiling*, not a bug: because vitals and the score timeline evaporate, there is no post-hoc "overshield uptime," "time under 25% health," or "when did team 1 pull ahead" from persisted data; overlays can't reconstruct historical frames after a reconnect (the server keeps no tick backlog; `request_events` backfills the *event* log only, and only while Live); and live spectator scrubbing is impossible. The tell that this boundary was *chosen but left ajar* is that the two hooks which would lift the ceiling — `snapshot_blob` and a `tick → pb:game_events` policy — were both built and both wired to nothing. `time_alive_ms` is a smaller instance of the same "read but dropped" pattern (the column exists and the writer sets it, but the end-of-game projection never populates it → persists as 0).

**Better? — Keep the default; wire one dormant hook only if replay is a goal (M, low-med).** Do not start persisting 30 Hz vitals by default — that would invert a sound cost decision. If match replay / scrubbing / richer post-match analytics are on the roadmap, the cheapest path is already scaffolded: (a) populate `games.snapshot_blob` at Live→Ready with a trimmed `instanceCache` JSON (decide trimmed-vs-full — an open question M13 left unresolved), giving a single-blob replay artifact per match without a new collection; and/or (b) ship a default-off `capture_policies` preset that routes the `event` class (not the raw `tick` firehose) to `pb:game_events` for series that want a durable event stream, keeping volume bounded. Either is additive and low-risk because the emit/sink plumbing already exists. Independently, fix the `time_alive_ms` drop in the end-of-game projection — a trivial correctness bug. Effort is **M** mostly because of the trimmed-vs-full `snapshot_blob` decision and testing, not the wiring.

## 5. Version-migration brittleness

Stewart flagged that cartographer "struggles with migration to newer versions," and which "version" is genuinely ambiguous. There are five axes; they are handled very differently, and the phrase most likely points at two of them.

**What.** The load-bearing fact: **PocketBase's own migration framework is not used at all** — no `pb_migrations/`, no `migrations/`, no `migratecmd`, no `jsvm`, no `OnBootstrap`. All 26 collections are defined in Go under `internal/pocketbase/schema/*.go` and (re-)applied on every boot inside `OnServe` via `RegisterAll` (`allschema.go:16-25`, `cmd/server/main.go:75-78`), calling the PocketBase core API directly (`core.NewBaseCollection`, `collection.Fields.Add(&core.TextField{…})`, `AddIndex`, `app.Save`). The dominant per-collection pattern is **create-fresh-or-touch-rules-only**, archetypally `games.go:20-24`: if the collection already exists, re-apply *only* its ACL rules and return; the field/index definitions run *only* on first creation. Registration order is a hand-maintained concern — `identity.go` is a ~40-line comment block sequencing five phases so cross-collection relations and rule subqueries resolve at save time.

**Why.** `CLAUDE.md:218-220` documents the framework posture: *"PocketBase v0.36.7 — uses `net/http.ServeMux`, NOT Echo. Hooks use `OnServe` not `OnBeforeServe`"* and *"schema/routes register inside OnServe via `RegisterAll()`"* with *"one `.go` file per logical domain."* The ordering rationale is `identity.go:3-7`: it is *"the single coordination point for schema registrations whose ordering matters — either because of cross-collection RelationFields … or because of PB rule references through the M08 hasAdminRole subquery."* The "batch schema changes early" philosophy is stated at `M07-identity-schemas.md:77`: *"schema-shape changes that future milestones depend on are cheaper to land here in one migration than to retrofit later."* And the one place the codebase reconciles an existing collection, it says why — `game_events.go:35-36`: *"Dev dbs are ephemeral, but keep prod upgrade-safe rather than silently skipping the new column."* **[doc]**

**Assessment — the two axes that actually bite:**

- ***App-schema evolution against an existing `pb_data` (most likely referent).*** Because of create-fresh-or-touch-rules-only, **adding a field and booting against an existing database silently does not create the field** — only a fresh `pb_data` gets the current shape. Every real schema change therefore needs a bespoke, hand-written, idempotent migration shim, and the repo has exactly three of these done by hand (`game_events.go:34-44` add-column-if-missing; `users.go:39-107` per-field `GetByName` guards; `gamertags.go:122-184` full add→backfill→drop for the 4-state status migration). The **dev DB is deliberately ephemeral** (`clean_on_exit` wipes `tmp/pb_data`, `CLAUDE.md:237`), so the create-fresh path is exercised constantly and the existing-DB reconcile path is under-exercised — meaning schema-drift bugs surface only in a **production upgrade**, which is precisely the reported symptom. There is a concrete scar: an alphabetical-init ordering bug once **crashed boot** with *"failed to load collection user_roles"* until `identity.go` was reordered (`CHANGELOG.md:87`). **[doc for the shims + crash; inf for "new fields silently don't appear," which follows directly from the code.]**

- ***PocketBase framework upgrades.*** Structurally the most dangerous, currently latent. The raw `core.*` field API is used across ~29 files with no migration-file insulation, and `go.mod` shows PocketBase has **never been bumped** off the v0.36.7 template pin (`go.mod` has only two commits ever, both scaffold). PocketBase reshapes exactly this surface between minors; because the whole `RegisterAll` runs on boot, a single changed constructor signature fails the entire server startup with no incremental safety net. The `OnServe`-not-`OnBeforeServe` note in CLAUDE.md is a fossil of a *prior* PB breaking change (the Echo→ServeMux / `OnBeforeServe`→`OnServe` swap in PB v0.23) — evidence this lineage has already eaten one PB migration. **[inf, well-founded]**

The other three axes are minor: the **Go toolchain** (`go 1.25.0`, no `toolchain` pin) builds cleanly on newer Go — almost certainly not the referent; **xemu/Halo build offsets** are a real pinned-version risk (see §3) but the documented pain is PC-vs-Xbox porting, not an observed xemu bump; the **frontend toolchain** (pnpm 10→11, Skeleton/Svelte/Tailwind majors) is the one axis with a *completed, documented* migration (`CLAUDE.md:240`, a dedicated `sveltekit/docs/NAV.md`), so it's a solved pain rather than a live one. ADR-0001 (version-from-git-tag) governs the *app's own version string* and is a genuinely clean, drift-free scheme — unrelated to the migration struggle.

**Better? — Refactor toward an explicit, ordered, idempotent migration runner (M, med).** The current model is "implicit migration by re-running schema code," which is fine for greenfield and painful for upgrades. Two viable directions, in increasing effort:

1. *Formalize what already exists.* Introduce a small in-repo migration registry: an ordered list of versioned, idempotent `up(app)` steps (the three existing shims become the first entries), run once inside `OnServe` after `RegisterAll`, recording applied versions in a tiny `schema_migrations` collection. This keeps the Go-defined-schema model but makes "evolve an existing DB" a first-class, ordered, testable path instead of ad-hoc per-collection reconciles. Low-to-medium risk; mostly organizing discipline.
2. *Adopt PocketBase's migration framework* (`migratecmd` + Go migrations) for schema changes going forward, keeping code-defined collections for initial creation. Higher effort and a larger conceptual shift, but it buys PB-native ordering, up/down, and a bump-survival story.

Whichever path, add one thing immediately regardless: **a CI/test that boots the server against a *seeded, non-empty* `pb_data` snapshot** (not just the ephemeral fresh DB), so existing-DB drift is caught before production. Also treat the PB version as a deliberate upgrade project when it happens — pin, read the PB changelog for `core.*` field-API deltas, and expect a coordinated multi-file edit. Effort **M**; risk **med** because it touches boot-time schema application, which is why the seeded-DB test matters.

## 6. SvelteKit SPA (adapter-static) + PocketBase same-origin

**What.** The frontend is a SvelteKit app built with `@sveltejs/adapter-static` into `pb_public/` (`svelte.config.js:16-23`, `fallback: 'index.html'`), served *from disk at runtime* by the Go binary — not embedded — via `apis.Static(os.DirFS("pb_public"), true)` registered *last* as a `GET /{path...}` catch-all so specific routes win, plus an auth-gated `GET /app/{path...}` shell (`routes/app.go`). Everything shares PocketBase's single `:8090` origin: the static SPA, `/api/*`, the kiosk reverse proxy, and the WebSocket endpoint. In production the SDK talks same-origin relative (`api-base.ts:9-11`), which eliminates CORS. cloudflared is the recommended single-public-port fronting (`README.md:163`) but is operator-managed — there is no tunnel config in the repo.

**Why.** `proxy.go:3-11` is the crisp statement: per-container xemu/browser ports are bound to `127.0.0.1`, unreachable over the internet, so *"All traffic flows through PocketBase's :8090, which is the single port that needs to be public when deploying behind a TLS reverse-proxy. Auth is enforced via the same PocketBase JWT."* `CLAUDE.md:99` reinforces *"only PocketBase's port needs to be public."* adapter-static (vs a Node adapter) means the whole frontend is static files a single Go binary serves with zero JS runtime, matching the "single binary runs everything" architecture; the SPA fallback enables client-side routing for dynamic routes unknown at build time. **[doc]**

**Assessment.** This is a strength and has aged well. For a self-hosted, single-box, one-public-port tool it is close to ideal: no CORS in prod, one binary, one origin, one tunnel. The costs are the ordinary sharp edges of the model, all documented: **route-namespace ordering is load-bearing** — the SPA catch-all shadows any future top-level path not registered before it, so a single misordered `register()` silently turns an API route into an index.html 200 (`CLAUDE.md:232`); and **trailing-slash discipline** is mandatory — `trailingSlash = 'always'` means every internal href must end in `/` or navigation breaks under the static adapter (`CLAUDE.md:234`). The kiosk proxy also strips `X-Frame-Options` and CSP to allow embedding (`proxy.go:83-88, 113-117`), which is justified by the token gate but means the only thing preventing clickjacking of the kiosk is the token (see §7).

**Better? — Keep (S hardening, low).** No structural change; the model fits the deployment. Small robustness additions: an automated test or lint asserting the static catch-all is registered last and that no `/api/*` path is shadowed; and a documented, checked-in reference cloudflared/reverse-proxy config (or at least a RUNBOOK section) so the "single public port" contract is reproducible rather than tribal. The same-origin coupling is a feature here, not a liability — resist the temptation to split the SPA onto its own origin, which would reintroduce CORS and a second deployable for no benefit at this scale.

## 7. Auth / routing — overlay-token, kiosk `?token=`, and the (nonexistent) "station-token"

**What.** First, a correction that matters for the retrospective: **there is no "station-token"** anywhere in the repo — not in Go, SvelteKit, docs, schema, `.env`, or the entire git history (exhaustively searched). The two real schemes are:

- **Overlay tokens** (`internal/overlaytoken/*`): a compact **HS256 JWT** carrying `{room, scope:"read", kid, exp}`, minted into an `overlay_tokens` registry collection (the `kid` is the authority), verified at the WS handshake by crypto-check *then* registry-check (exists, not revoked, not expired, room matches). Scope is exactly one — `read` — enforced in depth: a hub dispatch whitelist restricts overlay connections to `join_room`/`leave_room` before handler lookup, and room-scoping rejects anything but the token's bound `host:<instance>` room. Default TTL is **90 days**, deliberately long, *"set-and-forget for OBS; revocation is the real safety net"* (`registry.go:14-18`).
- **Kiosk `?token=`** (`routes/containers/{proxy,auth}.go`): this is a **normal PocketBase user JWT** passed in the query string (then upgraded to an HttpOnly path-scoped `kiosk_token` cookie for sub-resources), *because iframes and raw WebSockets cannot set an `Authorization` header* (`proxy.go:41-43`). Authorization is M09's `authorizeKioskAccess`: admins reach any container; a non-admin reaches only the container their gamertag is currently rostered in, re-checked per request with a 5-minute grace TTL.

**Why.** The separate overlay token was an explicit, owner-settled design question — `M10-overlay-revamp.md:43`: *"Stewart settled the design: a scoped, revocable, read-only overlay token is the OBS door, alongside the existing logged-in-operator door,"* because an OBS browser source *"can't carry a logged-in user's session"* (`token.go:1-7`) and a user JWT is neither room-scoped nor read-only. The two-door WS handshake tries a user JWT first, then the overlay token (`handler.go:37-53`). The kiosk query-param choice is a hard browser constraint, not a preference. The single-public-port framing ties back to §6. **[doc, extensively]**

**Assessment.** The overlay-token model is genuinely well-designed — scoped, revocable, read-only, defense-in-depth, with immediate revocation via the registry re-check on every handshake. It has aged well. The concerns are operational fail-open defaults and a couple of documented simplifications:

- ***Ephemeral-secret footgun (fail-open in prod).*** If `OVERLAY_TOKEN_SECRET` is unset, `main.go:47-53` generates a random secret at boot and only *logs a warning* — silently invalidating every minted token on each restart. This "works in dev, breaks quietly in prod."
- ***WS origin default is open.*** With `WS_ALLOWED_ORIGINS` unset, the handshake uses `InsecureSkipVerify: true` (all origins), and the VNC relay hard-codes it (`handler.go:91-98`, `vnc.go:47-50`). Auth is still required, but the CSWSH surface is wider than necessary by default.
- ***Query-string token exposure.*** Both the kiosk PB-JWT and the overlay token travel in the URL. The kiosk case is mitigated by the immediate HttpOnly-cookie hand-off, but the overlay token stays in the OBS Browser Source URL permanently; the design leans entirely on revocability + 90-day TTL as the compensating control, with no rotation mechanism and no automated expiry sweep of the registry.
- ***Documented simplifications:*** any authorized minter may mint a token for *any* room (no per-room ownership), and the 5-minute kiosk roster grace is a deliberate, Stewart-requested window where access outlives roster membership.

**Better? — Keep the model; close the fail-open defaults (S–M, low).** Highest value, lowest effort: **fail closed on a missing `OVERLAY_TOKEN_SECRET` in production** (refuse to start, or refuse to mint, rather than minting against an ephemeral secret) — this is a one-conditional change that removes a silent prod outage. Next: default `WS_ALLOWED_ORIGINS` to the app's own origin when unset in production (keep the open default only in dev). Consider moving the overlay token out of the URL into an HttpOnly cookie set on first load where the OBS/browser-source flow allows it, and add a periodic sweep that hard-deletes revoked/expired `overlay_tokens` rows. None of these touch the core scheme; they harden its edges. The per-room-ownership gap and roster grace are fine to leave as documented v1 trade-offs unless the threat model tightens.

## 8. The runner / vncinput arbitration

**What.** "Runner" names two distinct abstractions, which is worth stating plainly. (1) The **scraper runner** (`internal/scraper/manager/runner.go`, on every branch incl. `main`) owns one xemu instance's *read* path for its lifetime, hot-swapping its `GameReader` as the running title is recognized/unrecognized, driven single-goroutine through the Idle/Ready/Live machine. (2) The **host runner** (`internal/hostrunner/*`, on `feat/xemu-input-sendkey` only) is the *write* path: a state-aware auto-host state machine that reads `Observation`s (projected from the scraper's cache, never by touching a `GameReader` off-goroutine) and drives the lobby menus via an `Input` interface, gating every keypress on readable state — *"it advances only on confirmed observations … never by counting presses"* (`lobby.go`).

Input reaches xemu's Xbox controller through one of two channels into the SDL-gamepad path: a uinput virtual pad (`internal/vpad`, analog movement/aim) or the container's Xvnc keyboard (`internal/vncinput`, digital/menu), the latter emitting **byte-identical RFB `KeyEvent`s to the admin's `VNCKeyboard`** into the *same* `/websockify` endpoint the kiosk uses. Arbitration is explicit: an `Arbiter` (`internal/hostrunner/arbitration.go`) with `AuthRunner`/`AuthAdmin`/`AuthDisabled`; `TakeOver()` suspends the runner so its presses don't fight the admin's keysyms on the shared channel, and the runner checks `CanEmit()` at the top of every tick. Integration is throttled to a 400 ms host-tick interval decoupled from the scraper poll cadence, and gated behind `HOSTRUNNER_ENABLED` (default false).

**Why.** The channel choice is ADR-0003 (§9). The *arbitration* design — share one channel with the admin rather than invent a second input path — is documented in the `keysym.go` header and ADR-0003's Log: because the injector's bytes are identical to the admin's proven-working path, *"the injector drives the controller by construction, and admin + runner share one channel natively (satisfies take-over with nothing extra)."* The read-from-cache-not-reader constraint is a concurrency rule stated at `runner.go:120-123`: the reader's caches are not concurrent-safe, so anything looking at reader state from another goroutine must go through the cache — which is why the host runner is fed projected `Observation`s. **[doc]**

**Assessment.** The arbitration model is elegant and, on paper, correct: reusing the admin's exact channel means "admin takeover" is free rather than a second system to reconcile, and the `Arbiter` + `CanEmit()` gate gives a clean single-writer story. The "never blind" gated-sequence design is the right instinct for driving a stateful, slow-booting menu. Two real caveats:

- ***It is unverified live and off `main`.*** ADR-0003's Log is candid that full runner integration was landed logically + unit-tested but the final `sudo`-podman container-drive step was repeatedly sandbox-blocked, and that an earlier assumption (admin VNC keyboard drives the controller) was at one point flagged *"unverified and may itself be broken (a sendkey-style false-positive)"* before being confirmed. The whole subsystem is 27 commits ahead on a branch that has never merged to `main`.
- ***Residual shared-channel and focus fragilities.*** Admin and runner share *one* keyboard stream; if the arbiter is bypassed or lags, presses interleave. And RFB `KeyEvent`s only register when the container's Selkies canvas has DOM focus, so the injector must issue a focus-click and re-grab focus on reconnect — lose focus mid-session and presses silently drop. The two lobby "card" screens (map/gametype select) are navigated on *timed* fallback bracketed by readable checkpoints — the acknowledged blind spot, and the reason `feat/map-gametype-enumeration` (which reads the widget cursor to close it) is held off the deploy branch pending a readable MAP-carousel cursor.

**Better? — Keep the design; gate deploy on live verification (M to verify, med).** The architecture is right; don't redesign it. Before it ships: complete the live container-drive verification the sandbox blocked (this is deploy-gating, not optional — the arbitration story is only proven once two real drivers contend on a live instance); add an explicit test/assertion that `CanEmit()` truly serializes admin-vs-runner under contention; and treat the timed-blind card screens as a known limitation with a screenshot/observation checkpoint rather than trusting hands-free runs (consistent with the skill's own guidance). Merging ADR-0003's *decision* (not necessarily all the code) into `main`'s decision log is part of finding #3.

## 9. Read-only scraping + the controller-induction methodology (ADR-0003)

**What.** The production scraper is strictly read-only (`Pread`/`memsave`, never a guest write). The *offset-hunting* methodology layered on top is **"induce, then verify"**: read memory read-only while *inducing* a state change via injected controller input, and treat an offset as confirmed only when the induced value is observed to change at that address. The skill states the bar: *"An offset is only 'confirmed' when a value was induced in-game and observed to change at that address,"* with a confidence taxonomy where *"Only `runtime-verified` counts as real"* (`SKILL.md` §3). The induction side is the virtual-pad rig (`padpool.py` → Go `vpad`); the read side is `memsave`/`/proc`; blind menu steps are screenshot-verified. ADR-0003 is the decision that operationalized the *input* half of this loop for the backend.

**Why.** ADR-0003 (Accepted, 2026-07-10, on `feat/xemu-input-sendkey`) is thorough and empirical. Its context: the scraper *"has no way to send input into xemu … The player self-service hosting feature needs a headless, backend-owned input channel."* It tested QMP `sendkey` live and *falsified* it: *"`SendKeyHold("e", 900ms)` … issued cleanly … → biped displacement 0.0000; no observed effect. Positive control on the same biped via the padpool virtual-pad FIFO (`move 1`) → biped moved 1.74 world units."* The structural reason: xemu's keyboard→controller mapping is the SDL scancode path, while QMP `sendkey` delivers to the emulated i8042/USB keyboard — *"a different channel the Xbox game … never reads."* The decision: **`sendkey` is not the controller path** (keep it only for guest-keyboard/monitor keys); **the uinput virtual pad is the keystone**; and (from the Log) the *runner's* menu channel is the admin's RFB→Xvnc keyboard, reused byte-for-byte. **[doc]**

**Assessment.** This is the most rigorously-justified decision in the project — a live read→act→verify POC with a positive control, a falsified first candidate, and a structural explanation for *why* it failed. The methodology has aged extremely well; it is exactly the discipline that keeps a memory-scraper honest against a moving target. The one nuance worth surfacing for a retrospective is the **read-only boundary vs induced writes**: the *scraper* never writes, but the *induction rig* deliberately crosses into writes/input to force state (pad input, and in the skill's `cw.py`, direct `/proc` pokes). That is a bounded, hand-driven exception, not part of the production read path — but it inherits real hazards the skill documents as "walls": the H2 render-copy wall (poked health is recomputed, so H2 kills/score can't be write-induced — they need a *real* gameplay kill), and the CE system-link desync wall (a large position poke desyncs the netcode). So some offsets are confirmable *only* through genuine gameplay, not pokes — a permanent constraint on the methodology, correctly acknowledged.

**Better? — Keep (no change).** Nothing to refactor; this is a methodology, and a good one. The only action is documentation hygiene: ADR-0003 is the crown-jewel rationale for the entire input subsystem and it is invisible from `main` (finding #3). Its *decision and empirical result* belong in `main`'s decision log so the "why not sendkey" reasoning isn't re-litigated by anyone who only sees `main`. Keep the read-only production boundary exactly where it is, and keep induced writes quarantined to the hand-driven offset rig.

## Cross-cutting finding: ADR / decision-record governance

Stewart's brief referenced "ADR-0003 (vncinput-vs-vpad), ADR-0004, any others." Here is the ground truth, because it is itself a finding:

- `main`'s `docs/decisions/` contains **only ADR-0001 and ADR-0002**.
- **ADR-0003** *does* exist and *is* the sendkey-vs-uinput-pad decision (substantively "how to inject input," which is where the vncinput-vs-vpad split is settled — as *complementary* channels, in the ADR Log + `keysym.go`, not as a titled either/or). It is **Accepted** but lives only on `feat/xemu-input-sendkey` (and descendants), first added in commit `04f4c2d`. It is invisible from `main`.
- **ADR-0004** (ISO-boot provisioning) is likewise **Accepted** but only on `feat/iso-boot-provisioning`.
- Meanwhile `main`'s `M08-roles-permissions.md:41` says *"ADR-0003 is not needed"* — referring to a *different, never-written* roles decision. Two parallel workstreams independently reached for "the next number (0003)"; the roles one abandoned it, the input one used it. The result is a **numbering collision plus a dangling reference** that will actively mislead anyone reading `main`.

The decisions convention is otherwise good — `docs/decisions/README.md` defines an immutable-once-Accepted, supersede-don't-edit discipline, and the ADRs that exist are high quality. The problem is purely that load-bearing Accepted ADRs are **stranded on unmerged branches** while `main` is the branch everyone reads, and the numbering isn't reconciled across branches.

**Better? — Refactor the record, not the code (S, low).** Bring ADR-0003 and ADR-0004 (the *files* + the README index rows) onto `main` — a decision record should track *decisions*, which are made once, independently of whether the implementing feature branch has merged; an Accepted ADR living only on a feature branch defeats the purpose of the log. Resolve the 0003 collision (renumber the never-written roles reference in M08, or annotate it), so `main`'s decision index is internally consistent. This is documentation-only, reversible, and high-clarity-per-effort. It also removes a real hazard: someone reading `main` today would reasonably conclude the input-channel decision was never recorded.
