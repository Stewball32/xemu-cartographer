# Milestone 19 — Robustness + offset validation

> Split from the original M8 (Robustness + Discord + auth). The Discord pieces (commands, channel posting) are subsumed by M17; the auth-wrapping work is mostly addressed by M6a + M7c + M8 + M9c; multi-user UX is covered by M15/M16. What remains is the "make silent bad data become loud errors" work, plus general operational hardening.

- **19a. Runtime offset sanity checks.** Apply to both Halo: CE and Halo 2 (whenever it lands). Base-HVA range checks, magic-value probes, plausibility bounds on read values. Loud error (log + WS notification + admin debug page badge) on sanity-check fail.
- **19b. Field-level validation.** Use the M6c debug-page audit's "looks plausible / clearly broken" annotations as input — promote validated fields out of `unverified` status, file remaining `unverified` fields as offset-investigation tasks.
- **19c. PB queue + scraper resilience.** Polish M13d's queue logic; add metrics; ensure scraper restarts cleanly after PB outages.

Smoke test: deliberately corrupt an offset in the Halo: CE table → loud error fires within one read; recover by reverting; confirm no silent bad-data writes to PB.

- 2026-05-19: **closes the 2026-05-18 offset hypothesis**. Diagnostic logging added to both readers (`gate=` + raw value counters), then offsets re-derived via two memory-probe agent passes against a live `debug-host` container running Halo CE Xbox. Findings:
  - `readObjectTypes`: `RefAddrObjectTypeDefRangeLo` (0x1FC0D0) and `RefAddrObjectTypeDefRangeHi` (0x1FCBA4) are **literal address bounds**, not pointers to dereference. Halocaster.py:344 misled the Go port. Array of 11 type-def pointers lives at `RefAddrObjectTypeDefArray = 0x1FCB78`; count = (Hi - Array) / 4 = 11. Each pointer points to a struct in low-GVA space (engine .data, ~0x001FCxxx range) and must be translated via QMP per-pointer (`RefreshLowHVA`), not via `HighGVA` arithmetic. Per-type field at +0x00 is a self-pointer/vtable on Xbox (NOT a string pointer as halocaster.py:736 claimed) — names hardcoded from the fixed 11-type order. Datum size at +0x08 is correct.
  - `readPowerSpawnScenarios`: tag reference at scenario_item+0x5C is a **u32 tag handle** (high16=salt, low16=index, 0xFFFFFFFF=empty), not s32 tag index — halocaster.py:648 was wrong. itmc respawn time is at `tag_data+0x0C` directly as s16 seconds (no PC-style `+0x14 → ptr → +0x0C` indirection). Per-placement override at `scenario_item+0x0E` (previously misnamed `OffScenItemUnknownAttr`) takes precedence when non-zero. `TicksPerSecond=30` added; both reads multiplied by it so wire stays in tick units.
  - Also added `power_item_spawns[].gametype_mask` from `scenario_item+0x04` so consumers can distinguish per-gametype variants of the same physical placement (CTF rocket-spawn-30s vs Slayer rocket-spawn-120s at identical coordinates).
  - Verification (chillout seq=3 tick=2595955): `object_types` has all 11 entries with correct names + datum sizes; `power_item_spawns` has 16 entries (full chillout item array including grenade boxes); intervals match canonical Halo CE values (camo/overshield 60s default → 1800 ticks, rocket 120s → 3600, sniper/grenades 30s overrides → 900). downrush also fully populated (34 entries).

- 2026-08-15: **host-health telemetry (new `internal/hosthealth`) + netif-resolution hardening.** Both land under 19c's "operational hardening"; the telemetry piece is 19's core thesis (make silent bad state loud) applied to the host itself rather than to offsets.
  - **Motivation.** Real Xboxes on System Link report laggy CE gameplay, but only when an xemu-cartographer container is the host. Already investigated and ELIMINATED before this pass: resource contention (load 0.09 on 32 cores, zero containers running), CPU throttling (governor `performance`, PPT 89W vs 55W default, 37.9C vs 89.8C crit, Ryzen AI Max+ 395), the scraper itself (reads are `pread` on `/proc/<pid>/mem` per [internal/xemu/mem.go](../../internal/xemu/mem.go), not QMP `memsave`; translation happens once at Init; non-disruptive to the guest), the NIC binding (all four instance tomls correctly had `netif = 'enp191s0'`), and `SELKIES_FRAMERATE` (max *capture* rate off the virtual display, does not gate xemu's render rate). The Firefox sidecar is load-bearing — Selkies needs an attached client to keep streaming. **Root cause remains unknown**; this work exists to make it findable.
  - **What was missing.** `engine_tick` was already on the wire but nothing compared it to wall clock, so a struggling host was indistinguishable from a healthy one — the counter just climbs slower. Diagnosis required a manual capture + offline division.
  - **`internal/hosthealth`** — pure, injected clock, no PB/IO (the `internal/series` / `internal/rating` / `internal/rostergrace` pattern), 18 unit tests. `Tracker.Observe(tick, at)` + `Health(now)` → `{status, observed_hz, expected_hz, ratio, window_seconds, samples, measured_at, confident}`. Endpoint-to-endpoint estimator over a rolling 5s window (intermediate jitter cancels; ±1-tick quantization over the span = ±0.2Hz, against the 2Hz gap it must resolve). `window_seconds` reports the ACTUAL measured span, not the configured window.
  - **Three false-alarm sources, each handled explicitly** — this is most of the package: (a) the engine clock **re-inits to 0 at match start** (live-verified 2026-08-08, see [sveltekit/src/lib/utils/overlay-state.ts](../../sveltekit/src/lib/utils/overlay-state.ts)) → backwards step resets the window; (b) a menu / paused guest / Idle-phase runner (which reports a literal `tick=0`) has a **stopped**, not slow, counter → distinct `stalled` status keyed off time-since-last-*advance*, never `degraded`; (c) phase transitions jump the counter discontinuously (Idle's constant 0 → Ready's live free-running value, implying ~400kHz) → forward jumps beyond 4× expected + 30 ticks slack are treated as discontinuities. Plus a `confident` gate (min 2s span, min 8 samples) so no verdict is rendered off a sliver.
  - **Wiring.** Driven from `runner.recordIteration` — the one call every phase makes on every successful read — so the window is continuous across Idle → Ready → Live and is meaningful at a menu, not just mid-match. Snapshot stored in `instanceCache` as a pointer-free value so `readCache()`'s shallow copy stays race-free; seeded at construction so an un-sampled runner publishes a well-formed `unknown` rather than `status:""`. Surfaced as `host_health` on the per-instance **`game`-class envelope** and via `Manager.HostHealth` → a new `HealthSource` injection in `routes/scraper` → four rows in the **admin kiosk box view** diagnostics panel, which also carries `host_health_age_ms` (same staleness idiom as `readout_age_ms`: a wedged runner stops refreshing the snapshot while its last values keep looking healthy).
  - **Open / unverified.** The 30Hz expectation is the CE engine tick; `ExpectedHz` is a `Config` field so a future non-CE plugin can reuse the package. Not yet observed against a genuinely struggling host — the acceptance bar (healthy ~30.0, a slow host visibly lower) is proven in unit tests and by construction, but the real diagnostic value only gets confirmed the next time the lag reproduces. **That is the next step: reproduce the laggy-host report with a container hosting and read the panel.** If it reads ~30.0 while Xboxes still report lag, the engine tick is NOT the bottleneck and the investigation should move to the network path (pcap timing / packet pacing) rather than host compute.
  - **netif hardening** ([containers/xemu/init/02-patch-toml.sh](../../containers/xemu/init/02-patch-toml.sh)) — three latent defects, all currently masked by this box happening to resolve correctly: skip-if-present meant a stale `netif` from another machine was never corrected (now compare-and-rewrite); the exclusion list matched `br-*` but not `br0`/`bond0`, both of which sort before `enp191s0` (broadened to bridges/bonds/tunnels/wireless/overlay-VPNs); no carrier check (now requires `carrier == 1`, and warns + leaves the toml alone rather than falling back to any non-`lo` interface). `eno*` was **deprioritised rather than excluded** — it is a genuine onboard NIC and hard-excluding it would strand an `eno1`-only host, so it is outranked by `enp*`/`ens*` instead. New explicit `NETIF` override from the already-sourced `/custom-cont-init.d/.env` wins over autodetect, which is the only correct answer when a host has several plausible physical NICs. Verified against a fake `/sys/class/net` (16 cases: all three defects, the override, eno1-only, no-carrier-anywhere, and TOML-structure/QMP regressions).
