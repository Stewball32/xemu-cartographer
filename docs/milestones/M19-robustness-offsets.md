# Milestone 19 — Robustness + offset validation

> Split from the original M8 (Robustness + Discord + auth). The Discord pieces (commands, channel posting) are subsumed by M17; the auth-wrapping work is mostly addressed by M6a + M7c + M8 + M9c; multi-user UX is covered by M15/M16. What remains is the "make silent bad data become loud errors" work, plus general operational hardening.

- **19a. Runtime offset sanity checks.** Apply to both Halo: CE and Halo 2 (whenever it lands). Base-HVA range checks, magic-value probes, plausibility bounds on read values. Loud error (log + WS notification + admin debug page badge) on sanity-check fail.
- **19b. Field-level validation.** Use the M6c debug-page audit's "looks plausible / clearly broken" annotations as input — promote validated fields out of `unverified` status, file remaining `unverified` fields as offset-investigation tasks.
- **19c. PB queue + scraper resilience.** Polish M13d's queue logic; add metrics; ensure scraper restarts cleanly after PB outages.

Smoke test: deliberately corrupt an offset in the Halo: CE table → loud error fires within one read; recover by reverting; confirm no silent bad-data writes to PB.

- 2026-05-19: scenario envelope `player_spawns[].gametypes` shipping as a base64 string (`"DQABAA=="`) on live captures from two separate instances (`debug-host`@chillout, `debug-charlie`@downrush). Root cause: `ScenarioPlayerSpawn.Gametypes` was declared `[]uint8` ([internal/scraper/manager/scenario.go:64](../../internal/scraper/manager/scenario.go)), which Go's `encoding/json` aliases to `[]byte` and marshals as base64. Fix: changed the field to `[4]uint8` (fixed-size arrays of bytes don't trigger the special case) and adjusted the builder literal at [internal/scraper/manager/v2_adapters.go:202](../../internal/scraper/manager/v2_adapters.go). Frontend types in `sveltekit/src/lib/types/scraper-v2.ts` already expected `number[]`, so the wire fix unblocks the UI with zero parse-side change. Regression test added at `TestScenarioGametypesMarshalsAsArray` ([v2_adapters_test.go](../../internal/scraper/manager/v2_adapters_test.go)).

- 2026-05-19: partial follow-up on the 2026-05-18 entry's `readObjectTypes` / `readPowerSpawnScenarios` empty-slice observation. Read [internal/scraper/haloce/reader_cache.go:74-95](../../internal/scraper/haloce/reader_cache.go) found a separate bug independent of the offset question: `ensureScenarioStatic` set `Filled = true` unconditionally after the first attempt, so a transient empty return from either reader (engine pointers not yet warm at the moment of first fill) would lock empty results in for the entire scenario lifetime. Fix: per-field retry while empty, gate `Filled` on all critical readers actually producing data. **This does NOT close the 2026-05-18 candidate-offset hypothesis** — if the offsets themselves are wrong against Xbox memory, retries will still come back empty forever. Next verification step: capture a fresh scenario envelope from a long-running match. If `object_types` / `power_item_spawns` are populated → the original bug was just the cache-gating, no offset re-derivation needed. If still empty → the candidate offsets from the 2026-05-18 note are the real issue and the diagnostic-logging path applies. Until that verification lands, the 2026-05-18 entry stays open.

- 2026-05-19: follow-up regression on the prior cache-gating fix. Live captures after restart (`debug-host`@chillout seq=2 tick=2338921, `debug-charlie`@downrush seq=2 tick=2264482) showed MORE fields empty than before: `fog: null`, `memory_regions: null`, `player_spawns: []` — not just `object_types` and `power_item_spawns`. Root cause: `composeGameData` ([internal/scraper/haloce/reader.go:201](../../internal/scraper/haloce/reader.go)) gated _all_ scenario-cache field copies on `r.scenarioCache.Filled`. The earlier fix made `Filled` stay false until `ObjectTypes` and `PowerSpawnsScenario` populated; when those never populate (offsets potentially wrong against Xbox memory, per the 2026-05-18 hypothesis), `composeGameData` skipped the entire cache copy, dropping populated fields too. Fix: decouple the wire output from `Filled` — `composeGameData` now copies whatever's in the cache regardless of `Filled`, with a `if out.Map == ""` live-read fallback. `ensureMatchStatic`'s `InitialObjectIDs` gate also relaxed from `Filled` to `len(PowerSpawnsScenario) > 0` so it fires as soon as that single dependency is met (decoupled from `ObjectTypes`).

- 2026-05-19: verification of the cache-gating + composeGameData decoupling fix. Fresh captures (`debug-host`@chillout seq=3 tick=2350581, `debug-charlie`@downrush seq=3 tick=2273175) show `gametypes` as proper JSON number arrays, `fog` / `memory_regions` / `player_spawns` / `game_difficulty` all populated, but **`object_types: []` and `power_item_spawns: []` remain empty**. Verification verdict: the cache-gating regression is closed; the empty arrays are NOT a cache-coherency issue, confirming the 2026-05-18 hypothesis that `readObjectTypes` and `readPowerSpawnScenarios` have wrong offsets for the Xbox build. The 2026-05-18 entry stays open for offset re-derivation.
